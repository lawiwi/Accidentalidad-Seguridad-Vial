Etapa 3 · Construcción del proceso ETL

Extracción y transformación de vehículos mediante SSIS

Implementación del paquete SSIS ETL_Accidentalidad_Vial, encargado de extraer el archivo vehiculos_accidentes.csv hacia la zona de Staging y de aplicar, de manera secuencial, las reglas de tratamiento R01 a R09 definidas previamente, separando los registros aceptados de aquellos que requieren revisión.

01

Paquete ETL_Accidentalidad_Vial

La extracción y transformación de los datos de vehículos se desarrolló mediante un paquete SSIS independiente, ETL_Accidentalidad_Vial, construido en Visual Studio sobre la misma base de datos IntegracionSiniestrosVehiculos. Este paquete toma como fuente el archivo vehiculos_accidentes.csv y aplica, de manera secuencial, las reglas de tratamiento R01 a R09 establecidas en el diagnóstico inicial.

El paquete se organiza en dos Data Flow Task principales — DFT_01_Extraccion y DFT_02_Transformacion — coordinados por un Control Flow que además garantiza la repetibilidad del proceso sobre el mismo lote.

DATA FLOW 01 DFT_01_Extraccion Carga sin transformar el CSV en StagingVehiculos.
→
DATA FLOW 02 DFT_02_Transformacion Convierte, normaliza, deduplica y separa aceptados de revisión.
02

Data Flow de extracción — DFT_01_Extraccion

El primer Data Flow Task tiene como finalidad cargar el archivo vehiculos_accidentes.csv, sin transformar, en la tabla StagingVehiculos, conservando así los datos originales conforme al criterio de conservación definido para el proceso.

FLAT FILE SOURCE vehiculos_accidentes.csv Conexión con las 9 columnas del archivo: marca_vehiculo, modelo_vehiculo, tipo_vehiculo, edad_vehiculo, fecha_accidente, gravedad_accidente, departamento_accidente, municipio_accidente y autoridad_de_transito.
→
DATA CONVERSION Unicode string [DT_WSTR] El archivo plano interpreta el texto como cadenas no-unicode, mientras que StagingVehiculos utiliza columnas NVARCHAR.
→
OLE DB DESTINATION dbo.StagingVehiculos Inserta los registros convertidos, mapeando cada columna de salida a su equivalente en la tabla.

El Data Flow procesó exitosamente las 406.540 filas del archivo original, tanto en la lectura del Flat File Source como en la conversión y la carga final, un número que coincide con el total de registros identificado en el diagnóstico de la Etapa 2, confirmando que no se perdió ningún registro durante la extracción.

Para verificar que la carga se realizó correctamente, se consultó directamente la tabla StagingVehiculos en SQL Server Management Studio: 

SELECT MarcaVehiculo, ModeloVehiculo, TipoVehiculo, EdadVehiculo,
       FechaAccidente, GravedadAccidente, DepartamentoAccidente,
       MunicipioAccidente, AutoridadTransito
FROM dbo.StagingVehiculos;

La consulta confirmó que los 406.540 registros fueron almacenados correctamente en StagingVehiculos, sin modificaciones respecto al archivo original, quedando así disponibles para la etapa de transformación.

03

Tablas de destino: VehiculosLimpios y VehiculosRevision

Antes de configurar el Data Flow de transformación se crearon las dos tablas que reciben el resultado del tratamiento: VehiculosLimpios, para los registros aceptados, y VehiculosRevision, para los registros que requieren revisión, conservando su valor original y el motivo de la clasificación.

SALIDA ACEPTADOS VehiculosLimpios

Recibe los registros convertidos, normalizados y sin duplicados que cumplen las condiciones definidas.

Id · MarcaVehiculo · ModeloVehiculo · TipoVehiculo · EdadVehiculo · FechaAccidente · GravedadAccidente · DepartamentoAccidente · MunicipioAccidente · AutoridadTransito · FechaProceso
SALIDA REVISIÓN VehiculosRevision

Conserva el valor original de los campos y documenta el motivo de la clasificación.

Id · MarcaVehiculo · ModeloVehiculo · TipoVehiculo · EdadVehiculo · FechaAccidente · GravedadAccidente · DepartamentoAccidente · MunicipioAccidente · AutoridadTransito · MotivoRevision · FechaProceso 
CREATE TABLE dbo.VehiculosLimpios (
    Id                     INT IDENTITY(1,1) PRIMARY KEY,
    MarcaVehiculo          NVARCHAR(100),
    ModeloVehiculo         INT,
    TipoVehiculo           NVARCHAR(100),
    EdadVehiculo           INT NULL,
    FechaAccidente         DATE,
    GravedadAccidente      NVARCHAR(100),
    DepartamentoAccidente  NVARCHAR(100),
    MunicipioAccidente     NVARCHAR(100),
    AutoridadTransito      NVARCHAR(200),
    FechaProceso           DATETIME DEFAULT GETDATE()
);

CREATE TABLE dbo.VehiculosRevision (
    Id                     INT IDENTITY(1,1) PRIMARY KEY,
    MarcaVehiculo          NVARCHAR(100),
    ModeloVehiculo         NVARCHAR(50),
    TipoVehiculo           NVARCHAR(100),
    EdadVehiculo           NVARCHAR(50),
    FechaAccidente         NVARCHAR(50),
    GravedadAccidente      NVARCHAR(100),
    DepartamentoAccidente  NVARCHAR(100),
    MunicipioAccidente     NVARCHAR(100),
    AutoridadTransito      NVARCHAR(200),
    MotivoRevision         NVARCHAR(300),
    FechaProceso           DATETIME DEFAULT GETDATE()
);
i
Por qué dos tablas de destino

Separar los registros aceptados de los registros en revisión permite aplicar el criterio de no pérdida injustificada de información: ningún registro se elimina, únicamente se clasifica según el resultado de las validaciones.

04

Data Flow de transformación — fuente y conversión de tipos

El Data Flow DFT_02_Transformacion toma como fuente la propia tabla StagingVehiculos mediante un componente OLE DB Source configurado en modo SQL Command: 

SELECT MarcaVehiculo, ModeloVehiculo, TipoVehiculo, EdadVehiculo,
       FechaAccidente, GravedadAccidente, DepartamentoAccidente,
       MunicipioAccidente, AutoridadTransito
FROM dbo.StagingVehiculos;

A partir de esta fuente, el primer componente aplicado fue Data Conversion, encargado de convertir FechaAccidente a tipo fecha (DT_DATE) y EdadVehiculo y ModeloVehiculo a tipo entero (DT_I4), atendiendo la regla R06.

Durante las pruebas se identificó que los 20 registros con edad_vehiculo nulo provocaban un error de conversión al intentar transformar una cadena vacía en un número. Para evitar que esto interrumpiera el procesamiento del resto del lote, se configuró el Error Output del componente en modo “Redirect row” para la columna EdadVehiculo_conv, de manera que esas filas se separan automáticamente hacia un flujo independiente que las envía a VehiculosRevision, conservando el valor original — implementando así la regla R03.

OLE DB SOURCE StagingVehiculos 406.540 filas recibidas.
→
DATA CONVERSION DT_DATE / DT_I4 406.520 filas continúan hacia la transformación.
→
ERROR OUTPUT OLE DB Destination 20 filas con edad vacía redirigidas a VehiculosRevision.

El componente confirmó el comportamiento esperado: de las 406.540 filas recibidas, 20 fueron redirigidas por el Error Output directamente hacia VehiculosRevision, mientras que los 406.520 restantes continuaron por el flujo principal.

05

Derived Column: normalización de texto y banderas de calidad

Sobre las filas que superaron la conversión se aplicó un componente Derived Column, encargado de implementar las reglas R02, R04, R05 y R07 mediante las siguientes columnas derivadas:

Columna derivada Expresión (SSIS) Regla
MarcaVehiculo_limpia (TRIM(MarcaVehiculo)=="" || ISNULL(MarcaVehiculo)) ? "NO REGISTRADA" : UPPER(TRIM(MarcaVehiculo)) R02
TipoVehiculo_limpio / DepartamentoAccidente_limpio / MunicipioAccidente_limpio / AutoridadTransito_limpia UPPER(TRIM(campo)) R07
EdadAtipica EdadVehiculo_conv > 40 R04
ModeloPosteriorAccidente ModeloVehiculo_conv > YEAR(FechaAccidente_conv) R05
!
Hallazgo documentado

El predicado configurado en el paquete evalúa EdadVehiculo_conv > 40; en el análisis de la Iteración 1 se identificó que la etiqueta exportada para este motivo indicaba un umbral distinto, por lo que quedó documentado como un aspecto a alinear en la siguiente iteración.

06

Sort: identificación y eliminación de duplicados

Sobre las columnas ya normalizadas y convertidas se aplicó un componente Sort, configurado con la opción “Remove rows with duplicate sort values” activada sobre la totalidad de las columnas del registro.

Esta configuración implementa la regla R01: dos filas se consideran duplicadas únicamente cuando coinciden en la totalidad de sus valores, ya normalizados y convertidos, evitando así eliminar registros que solo parecen similares.

07

Conditional Split: separación de aceptados y en revisión

El resultado del Sort se dirige hacia un componente Conditional Split que evalúa la condición EdadAtipica || ModeloPosteriorAccidente. Los registros que la cumplen se dirigen a la salida Revision (reglas R04 y R05); el resto se dirige a la salida por defecto Aceptados.

Antes de insertar los registros de la rama Revision en VehiculosRevision, un segundo Derived Column (DER_MotivoRevision) construye el texto que documenta el motivo de la clasificación, conforme a la regla R09 de trazabilidad: 

EdadAtipica && ModeloPosteriorAccidente
    ? "Edad atipica y modelo posterior al accidente"
    : (EdadAtipica
        ? "Edad atipica (>40 anios)"
        : "Modelo posterior al anio del accidente")
SORT 258.945 filas 406.520 filas − 147.575 duplicados exactos.
→
ACEPTADOS 250.299 filas Salida por defecto del Conditional Split.
→
REVISIÓN 8.646 filas Edad atípica o inconsistencia modelo/año.

Los resultados obtenidos en la primera iteración fueron los siguientes: de los 406.520 registros que llegaron al Sort, se identificaron y eliminaron 147.575 duplicados exactos, quedando 258.945 registros. De estos, 250.299 fueron aceptados y 8.646 fueron enviados a revisión por edad atípica o por inconsistencia entre el modelo y la fecha del accidente, sumándose a los 20 registros ya separados por el Data Conversion. En total, VehiculosRevision reúne 8.666 registros.

08

Control de repetibilidad del proceso

Conforme al criterio de repetibilidad definido para el proyecto, el paquete debe poder ejecutarse nuevamente sobre el mismo lote sin generar registros duplicados adicionales. Para garantizarlo, se incorporó al Control Flow un Execute SQL Task (SQL_TruncateTodo) que se ejecuta antes de los dos Data Flow Task y que vacía las tres tablas involucradas: 

TRUNCATE TABLE dbo.StagingVehiculos;
TRUNCATE TABLE dbo.VehiculosLimpios;
TRUNCATE TABLE dbo.VehiculosRevision;

De esta manera, cada ejecución completa del paquete parte siempre de un estado limpio, evitando que corridas repetidas acumulen copias adicionales de los mismos registros.

01 SQL_TruncateTodo Vacía Staging, Limpios y Revisión
→
02 DFT_01_Extraccion Carga el CSV en StagingVehiculos
→
03 DFT_02_Transformacion Convierte, deduplica y separa el resultado
i
Restricción de precedencia

Cada tarea del Control Flow solo se ejecuta si la anterior finalizó correctamente, evitando que un Data Flow procese información sobre una tabla que no fue vaciada previamente.

09

Verificación de resultados de la primera iteración

Finalmente, se verificaron los conteos finales directamente en SQL Server: 

SELECT COUNT(*) AS Limpios  FROM dbo.VehiculosLimpios;
SELECT COUNT(*) AS Revision FROM dbo.VehiculosRevision;
