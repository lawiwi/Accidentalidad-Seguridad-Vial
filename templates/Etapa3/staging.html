Etapa 3 · Modelo de datos y Staging

Creación del modelo relacional y proceso de Staging

Construcción de la base de datos en SQL Server, definición del modelo entidad-relación y preparación de las fuentes de datos mediante SQL Server Integration Services (SSIS) para las posteriores iteraciones de tratamiento de calidad.

01

Construcción de la estructura de datos

Como primera actividad de esta etapa se construyó la base de datos IntegracionSiniestrosVehiculos utilizando SQL Server Management Studio (SSMS). Sobre esta base se definió el modelo relacional que permitirá organizar la información proveniente de los archivos siniestros.csv y vehiculos.csv.

El diseño se realizó considerando las características de las fuentes originales y los problemas de calidad identificados previamente. Por esta razón, las entidades fueron separadas según su naturaleza y se establecieron claves primarias, claves foráneas y restricciones de integridad para controlar la estructura de los datos.

El modelo está compuesto por entidades geográficas, una dimensión temporal y entidades específicas para los registros de siniestros y vehículos. Esta organización permite separar información descriptiva repetitiva de los registros principales y proporciona una estructura adecuada para las posteriores transformaciones del proceso ETL.

02

Creación de la base de datos en SQL Server

La primera instrucción ejecutada corresponde a la creación de la base de datos que centraliza las estructuras utilizadas durante el proceso de integración. 

CREATE DATABASE IntegracionSiniestrosVehiculos;
GO

USE IntegracionSiniestrosVehiculos;

La creación de una base de datos independiente permite mantener separadas las estructuras propias del proyecto y facilita la administración de las tablas utilizadas durante las diferentes fases del proceso de integración.

03

Modelo entidad-relación

Una vez creada la base de datos se construyó el modelo entidad-relación a partir de las variables disponibles en ambas fuentes. El propósito del modelo es representar de manera estructurada las entidades que participan en el proceso de integración y establecer las relaciones que pueden ser sustentadas por los datos originales.

El modelo está conformado por las entidades Departamento, Municipio, DepartamentoMunicipio, Fecha, Siniestro, ClasificacionSiniestro, Hipotesis, MedioConocimiento, Vehiculo, Marca, TipoVehiculo, GravedadAccidente y AutoridadTransito.

La estructura utiliza claves primarias para identificar individualmente los registros y claves foráneas para establecer las relaciones entre las entidades. También se incorporaron restricciones UNIQUE y CHECK con el propósito de controlar duplicidades y valores que no cumplen las condiciones definidas para determinados atributos.

04

Estructura geográfica y jerarquía Departamento–Municipio

La información geográfica presente en ambas fuentes se estructuró mediante las entidades Departamento, Municipio y DepartamentoMunicipio. Esta separación permite representar la jerarquía geográfica sin repetir continuamente los nombres de los departamentos y municipios dentro de los registros principales.

La tabla Departamento contiene el identificador y nombre de cada departamento. La tabla Municipio contiene los municipios identificados en las fuentes. Finalmente, DepartamentoMunicipio funciona como entidad asociativa y almacena la combinación entre ambos niveles geográficos mediante las claves foráneas IdDepartamento e IdMunicipio.

De esta manera se representa la jerarquía Departamento → Municipio. La restricción de unicidad establecida sobre la combinación de ambas claves evita registrar repetidamente una misma relación geográfica.

05

Dimensión temporal

Para centralizar la información temporal se creó la entidad Fecha. Esta tabla contiene la fecha completa y diferentes atributos derivados como año, trimestre, número y nombre del mes, número de día y día de la semana.

La dimensión temporal es compartida por las dos fuentes, pero cada entidad mantiene su propia referencia. En Siniestro se utiliza IdFechaHecho, correspondiente a la fecha del hecho registrado, mientras que en Vehiculo se utiliza IdFechaAccidente, correspondiente a la fecha registrada para el vehículo.

Esta diferencia es importante para el modelo, debido a que compartir una dimensión de fecha no implica que un registro de siniestro y un registro de vehículo representen necesariamente el mismo evento.

i
Consideración de diseño

La dimensión Fecha permite realizar análisis temporales conjuntos, pero no constituye por sí misma una clave suficiente para establecer una relación directa entre Siniestro y Vehiculo.

06

Entidad Siniestro

La entidad Siniestro representa la información procedente del archivo siniestros.csv. En esta tabla se almacenan los identificadores del siniestro y del hecho, las coordenadas geográficas, los valores relacionados con muertos, víctimas y lesionados, la fecha del hecho, el tipo de lugar y el código del caso.

Adicionalmente, la entidad contiene referencias hacia DepartamentoMunicipio, Fecha, ClasificacionSiniestro, Hipotesis y MedioConocimiento. De esta manera, los valores descriptivos se mantienen separados de los registros principales.

Entidad Vehiculo

La entidad Vehiculo representa los registros provenientes del archivo vehiculos.csv. Contiene información relacionada con el año del modelo, edad del vehículo, fecha del accidente y ubicación geográfica.

La entidad también mantiene referencias hacia Marca, TipoVehiculo, GravedadAccidente y AutoridadTransito. Esta separación permite evitar la repetición de información descriptiva y mantener una estructura normalizada.

08

Ausencia de relación directa entre Siniestro y Vehiculo

Una decisión fundamental del modelo consiste en mantener independientes las entidades Siniestro y Vehiculo. No se creó una clave foránea IdSiniestro dentro de la tabla Vehiculo ni una relación directa entre ambas entidades.

Esta decisión se debe a que las fuentes utilizadas no proporcionan un identificador común que permita establecer de manera inequívoca qué vehículo corresponde a un determinado siniestro. Los identificadores disponibles tienen naturalezas diferentes: la fuente de siniestros utiliza IdSiniestro e IdHecho, mientras que la fuente de vehículos utiliza IdVehiculo.

Aunque ambas fuentes contienen información temporal y geográfica, compartir una fecha, departamento o municipio no es suficiente para afirmar que dos registros representan exactamente el mismo evento. Utilizar estos atributos como una relación directa podría generar asociaciones incorrectas.

10

Creación de la zona de Staging

Una vez definido el modelo relacional se creó una zona intermedia de almacenamiento denominada Staging. Esta capa permite recibir los registros directamente desde las fuentes originales antes de aplicar las transformaciones correspondientes al proceso de calidad de datos.

Se crearon las tablas StagingSiniestros y StagingVehiculos. Cada una conserva las variables provenientes de su respectivo archivo CSV y constituye el punto de partida para las transformaciones que serán realizadas posteriormente mediante SSIS.

Función del Staging

La zona de Staging permite separar la extracción de las transformaciones, facilitando la trazabilidad, validación y repetición del proceso durante las diferentes iteraciones de tratamiento de calidad.

11

Justificación de la zona de Staging

El Staging funciona como una capa intermedia entre las fuentes originales y el modelo relacional final. Su implementación permite que los datos sean recibidos desde los archivos CSV sin modificar inmediatamente su estructura definitiva.

Esta separación facilita la trazabilidad, debido a que permite conservar los registros obtenidos desde las fuentes antes de ejecutar las transformaciones. También facilita la repetibilidad, ya que las operaciones de limpieza y transformación pueden ejecutarse nuevamente a partir de los datos almacenados en Staging.

En el contexto de este proyecto, esta característica es especialmente importante porque el tratamiento de calidad se desarrolla mediante diferentes iteraciones. El Staging proporciona un punto de partida controlado para comparar los resultados obtenidos después de cada transformación.

12

Implementación del Staging mediante SSIS

Después de crear las estructuras de la base de datos se desarrolló el paquete de integración utilizando SQL Server Integration Services (SSIS) dentro de Visual Studio.

El paquete se configuró mediante un Control Flow que contiene dos tareas de tipo Data Flow Task. La primera corresponde a la carga de los registros de siniestros y la segunda a la carga de los registros de vehículos.

DATA FLOW 01 Staging Siniestros siniestros.csv → StagingSiniestros
DATA FLOW 02 Staging Vehiculos vehiculos.csv → StagingVehiculos
13

Flujo de datos de Siniestros

Dentro del Data Flow Staging Siniestros se configuró un componente Flat File Source encargado de establecer la conexión con el archivo siniestros.csv.

En la configuración de la fuente se verificaron las características del archivo, incluyendo su delimitador, separación de columnas, nombres de variables y tipos de datos. Los campos de texto fueron configurados como cadenas y los campos numéricos se configuraron utilizando tipos enteros cuando correspondía.

Esta configuración permite que SSIS interprete correctamente la estructura del archivo antes de enviarla al componente de destino. La revisión es necesaria debido a que una configuración incorrecta podría provocar errores de conversión, desplazamiento de columnas o incompatibilidad con la tabla de destino.

14

Destino OLE DB y mapeo de Siniestros

Después de configurar la fuente se incorporó un componente OLE DB Destination. Este componente establece la conexión entre el flujo de datos de SSIS y SQL Server, permitiendo seleccionar la base de datos IntegracionSiniestrosVehiculos y la tabla de destino StagingSiniestros.

En la sección de mapeo se estableció la correspondencia entre las columnas provenientes del archivo CSV y las columnas de la tabla de Staging. Durante este proceso fue necesario revisar manualmente algunas asignaciones debido a modificaciones realizadas previamente en los nombres de las variables.

La revisión del mapeo garantiza que cada variable de la fuente sea almacenada en la columna correspondiente y permite detectar posibles errores antes de ejecutar la carga.

15

Flujo de datos de Vehículos

Para la segunda fuente se implementó un flujo equivalente mediante el Data Flow Staging Vehiculos. El proceso inicia con un Flat File Source configurado para utilizar el archivo vehiculos.csv.

Se verificó nuevamente la estructura del archivo, incluyendo delimitadores, columnas y tipos de datos. Posteriormente, los registros fueron dirigidos hacia un componente OLE DB Destination configurado para cargar la información en la tabla StagingVehiculos.

16

Ejecución del Control Flow

Una vez configurados los dos flujos de datos se ejecutó el Control Flow del paquete SSIS. Durante esta ejecución, cada archivo CSV fue leído por su respectivo Flat File Source y posteriormente los registros fueron enviados mediante OLE DB Destination hacia las tablas de Staging.

En esta primera ejecución no se aplicaron transformaciones de calidad sobre los registros. El objetivo de esta fase consiste en realizar únicamente la extracción y carga inicial, dejando los datos disponibles en Staging para las transformaciones que serán implementadas durante las siguientes iteraciones.

Verificación de los datos cargados

Después de ejecutar el paquete SSIS se realizó una verificación directamente en SQL Server con el propósito de comprobar que los registros fueran almacenados correctamente en las tablas de Staging. 

SELECT *
FROM StagingSiniestros;

SELECT *

SELECT COUNT(*) AS TotalRegistros
FROM StagingSiniestros;

SELECT COUNT(*) AS TotalRegistros
FROM StagingVehiculos;
